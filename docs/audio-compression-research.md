# 音频压缩调研：能不能压、压成什么

状态：**已实施**（2026-09-19 Kim 拍板「音频也压缩 + 独立开关」，当日实现合入；部署随常规发布）
日期：2026-09-19
范围：apps/web 上传管道中对**用户上传音频**的转码（录音管道已自带编码，不在此列）
关联：图片方案 `docs/image-compression-design.md`（设置项与管线骨架可共用）

---

## 1. 现状

- **录音管道已经是 Opus**：`apps/web/src/lib/audio-capture/encoder.ts` 内置 WASM libopus + Ogg 封装（依赖 `@audio/encode-opus@1.3.0`），产出 `audio/ogg`，WAV 兜底。**应用生态已押注 Opus。**
- **用户上传的音频原样存储**：文件选择 / API 传什么存什么（mp3 / m4a / wav / flac…），服务端无 MIME 白名单、限 25 MiB。
- inline 白名单已含 audio/ogg、audio/mpeg、audio/aac、audio/wav、audio/webm（`attachment-http.ts`）。

**25MiB 上限的现实约束**：CD 音质 WAV 约 10.6MB/分钟，立体声超 2 分钟就传不上来；FLAC 单曲 30–80MB 也超限。所以现状下大音频本来就被挡在门外——转码的真实价值是：① 小于 25MiB 的未压缩音频省配额省加载；② 若未来放宽上限支持长音频/音乐，**必须先有转码**才放得开。

## 2. 能不能压：能，但只压"未压缩源"

| 源格式 | 是否转码 | 理由 |
|---|---|---|
| WAV / AIFF（无压缩） | **转** | 收益巨大（约 10–14×） |
| FLAC / ALAC（无损压缩） | **转**（待拍板，见 §6） | 约 8–10×，但放弃无损 |
| mp3 / AAC / m4a / ogg / opus | **不转** | 已是有损，二次转码纯代际损失，收益小 |
| 其他冷门格式 | 不转 | 解码都未必支持，原样上传 |

## 3. 压成什么：Opus，容器对齐录音管道（Ogg）

- **Opus 是当前最优解**：同码率音质最好的通用格式（语音 16–24kbps、音乐 64–128kbps 级别）、开放免专利费、**应用录音资产已经是 Opus**，播放器/转写/下载全链路一致。
- **容器**：与录音管道对齐用 **Ogg**。注意点（如实记录）：Ogg 容器在 Apple 平台的播放支持历史上不全。**实测结论（2026-09-19 复核）：Ogg Opus 播放是 Safari 18.4 / iOS 18.4（macOS 15.4）才加入的能力**——caniuse 长期标 limited 指的就是这段。因此转码前要先证明**这台浏览器真能解码我们的产物**：用同一编码器现场生成一条完整小流（20ms 静音帧 + flush ≈ 225 字节，含 OpusHead/OpusTags/EOS）喂 `decodeAudioData`，解不出就原样上传。不可省的理由有二：① 能力字符串不能当证据——WebKit 有对 Ogg 报 `"probably"` 却根本解不了容器的历史；② 反过来 `canPlayType` 在 Safari 上还有假阴性，纯字符串判断会把本来能压的设备也挡掉。**踩过的坑**：只 flush 不编码得到的「纯头 + EOS」流（163 字节）被 Chromium 拒绝（`EncodingError`），所以静音帧是必须的；同时源头解码出 0 个采样时也要提前返回，否则产出的正是这种播不了的文件。两条均已用真实 Chromium 实测确认。不过门就**原样上传**，否则会出现「在用户自己这台设备上上传的音频，回头播不出来」——这比体积大严重得多。本应用录音管道在旧 Safari 上同样播不了 Ogg，那是既有问题、单独处理；但转码不该把一个原本能播的 WAV 变成播不了的 Ogg。
- **ASR 兼容**：转码产物与录音同容器，MiniMax 批式管道已在吃 Ogg Opus，零适配。

## 4. 浏览器编码路径（2026 现状）

| 路径 | 支持 | 结论 |
|---|---|---|
| **复用现成 WASM libopus**（`@audio/encode-opus`，已在依赖里） | 全浏览器一致（wasm 无兼容问题） | **首选，零新依赖** |
| WebCodecs AudioEncoder | Chrome 94+ / Firefox 130+ / **Safari 26+（2026 补齐）** | 可作支持浏览器上的快路径（快于实时、省电），旧设备 wasm 兜底 |
| MediaRecorder | 全平台 | **否**——实时录制，60 分钟文件要等 60 分钟 |
| ffmpeg.wasm | 全平台 | **否**——约 25MB，杀鸡用牛刀 |

**风险项（实现时先验证）**：`@audio/encode-opus` 录音场景只用了 16kHz 单声道（`CAPTURE_SAMPLE_RATE`）；需确认封装支持 48kHz / 立体声 / 任意码率。不支持则换封装或改参——Opus 编码器本体能力齐全，问题只会在封装层。

**解码与重采样**：`decodeAudioData` 解码 WAV/FLAC（FLAC 支持度实现时验证）；Opus 只接受 8/12/16/24/48kHz。**实现定案**：`OfflineAudioContext` 的采样率取源头解析出的采样率（clamp 到 8–48kHz），而不是一律 48k——低采样率录音（16kHz 语音）按原速率解码只要 1/3 的内存，编码器（`toOpusRate`，Lanczos-3）自己在内部升到 48k。解析不出头部就退回 48k。

**内存上限（实现补充）**：`decodeAudioData` 会把整段音频解成 Float32（每采样每声道 4 字节），一条头里声称 3 小时的低采样率 FLAC 能一次吃掉几百 MB 内存、直接崩掉移动端标签页。所以解码前先读 RIFF/AIFF/FLAC 头估算解码后体积（`totalSamples × 速率缩放 × 声道 × 4`），超过 **96MB** 就跳过转码、原样上传；头部解析不出来时按 6 倍文件体积保守估算。这条与「压缩是装饰、永不阻塞上传」同源——宁可传大文件，也不能让上传把页面搞崩。

## 5. 收益量级

| 源 | 目标 | 压缩比 |
|---|---|---|
| WAV CD 立体声 1411kbps | Opus 96kbps | ≈ 14× |
| 语音 WAV 16k 单声道 256kbps | Opus 24kbps | ≈ 10× |
| FLAC（~900kbps） | Opus 96kbps | ≈ 9×（代价：放弃无损） |
| mp3 320kbps | — | 不转（代际损失不值 3×） |

码率起步两档：采样率 ≤24k 或单声道 → 24kbps；否则 96kbps（实现时按听感调）。

## 6. 建议形态与待拍板

- **独立开关**：设置里与「图片压缩」并排一行「音频压缩」，独立于图片开关（FLAC 转码是"降级为有损"，用户得能单独关）。
- **决策记录（2026-09-19）**：
  1. FLAC/ALAC 默认转码（开关可关）。
  2. 25MiB 上限 v1 不放宽。
  3. 码率落地为单声道 32 kbps / 立体声 96 kbps（较本文 24k 建议略调高，保语音清晰度）。
  4. **回放门禁（单一，但用真实字节）**：现场生成一条完整小 Opus 流并 `decodeAudioData` 解它——解不出就不转码（覆盖 Safari / iOS < 18.4，也覆盖 canPlayType 谎报）。见 §3。
  5. **解码内存门禁**：估算解码后 PCM > 96MB → 不转码。
  6. **空解码门禁**：`buffer.length === 0` → 不转码（否则产出播不了的纯头文件）。
  7. 开关文案如实写「无损 → 有损 Opus」（8 语言同步改；原稿写「未压缩」，而 FLAC 是无损压缩、并非未压缩）。
- **审计修正（2026-09-19，实现后复核）**：以上 4/5/6 与「按源采样率解码」四项，是提交 `30eb21c` 之后逐行审计补上的——原实现一律按 48k 解码、无回放/内存门禁、文案把 FLAC 说成未压缩。另：编码分块从 20ms 改为 1s（实测 11025Hz 源在 20ms 分块下 10 秒短 0.018%，1s 分块零误差，且输出字节数完全相同）。播放器另修一处：Ogg 时长未知时 `duration` 为 `Infinity`，会渲染成 `Infinity:NaN:NaN`。测试从 17 例增至 25 例。
- **工作量**：实际约 1 天（解码 + 编码两步，`decodeAudioData` 自带重采样，无需单独重采样层；`@audio/encode-opus` 验证支持任意采样率/声道/码率，风险解除）。
- **服务端不做**：约束与图片结论相同（免费版 CPU 10ms、128MB 内存、R2 无内置转码）。
